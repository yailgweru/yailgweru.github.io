# CLAUDE.md

Instructions for whoever (human or Claude) works on this repository —
Young AI Leaders Gweru Hub, a static site served from GitHub Pages at
`https://yailgweru.github.io/`.

## What this is

A no-build, static site. `index.html` is a single-page app: a Three.js
night-city scene (loaded from a CDN `<script>` tag) with floating "anchor"
nodes for each content section, and a hologram sidebar that shows each
item's full content.

**The JSON files are for updating the site only — the browser never reads
them** (steering D-30). You edit:

- `data.json` — site copy, SEO metadata, sections and their items, forms,
  Firebase config, and the 3D anchor layout
- `data/team/<slug>.json` and `data/projects/<slug>.json` — one person or
  project per file (see "People and projects")
- blog drafts (see "Blogs"), which `publish_blog.py` records in
  `blogs/manifest.json`

…then run `python scripts/update_site.py`, which renders all of it into
static HTML: a hidden `#hub-content` tree inside `index.html` holds every
section, item and sidebar panel as semantic HTML. Search engines read that
tree as-is (it's the SEO content), and at runtime the page builds the 3D
anchors, holo panels and sidebar from the same markup. `index.html` has no
hand-written copy, and no `fetch()` of JSON ever happens.

Preview with any static file server from the repo root:

```
python -m http.server 8000    # then open http://localhost:8000/
```

**Double-clicking `index.html` (`file://`) works too**, because all the
content is already in the HTML. Two things need a real server:

- Blog post bodies in the sidebar are fetched from `blogs/<slug>.html`;
  under `file://` the panel shows the post's excerpt instead (no request
  is made, so there's no console error).
- Forms submit to Firebase, so test them over `http(s)`.

The 3D scene's center logo disc is a WebGL texture, which Chrome refuses
to load from a `file://` path, so it uses a generated inline base64 copy
(`INLINE-LOGO:START`/`END`) in both modes. The web app manifest `<link>` is
added by a tiny inline script only over `http(s)` for the same reason.

## The one command: `python scripts/update_site.py`

Run it after **any** edit to `data.json`, `data/team/`, `data/projects/`,
`assets/logo.png`, or after publishing/removing a blog post. Nothing on
the site changes until you do. In order, it runs:

1. `build_pages.py` — standalone SEO pages `team/<slug>.html` and
   `projects/<slug>.html`
2. `build_form_rules.py` — `firebase/firestore.rules` from the forms in
   `data.json`
3. `prerender_seo.py` — `index.html`'s head, JSON-LD, brand bar and the
   `#hub-content` tree; the blog cards in `blogs/index.html`
4. `inline_logo.py` — `logo.png` into the inline WebGL texture
   (+ `make_favicons.py` when `logo.png` is newer than the favicons)
5. `build_feed.py` — `feed.xml`, the RSS feed of blog posts
6. `build_sitemap.py` — `sitemap.xml` from every real page (last, so its
   git-based `lastmod` dates see everything the steps above rewrote)

All of them load the JSON through `scripts/site_content.py`, which
validates everything first: if any file has a problem (bad URL, unknown
project owner, missing photo…), every problem is printed and nothing is
written. Every step only writes files whose content changed, so a second
run is a no-op.

## Steering — read before significant work

`steering/` holds the *what and why*; this file holds the *how*. Before
any significant change (new section, redesign, content push, policy
change), read `steering/direction.md` and check the work against its
principles and open questions. When a decision is made, append it to
`steering/decisions.md` (and drop the matching open question from
`direction.md`); after a meaningful change ships, add an entry to the top
of `steering/history.md`.

`docs/architecture.md` and `docs/structure.md` hold older background
notes. This file (CLAUDE.md) is the source of truth for how the project
is organized; `steering/` is the source of truth for why.

## Git workflow — commit as you go

**Commit whenever something meaningful changes.** Don't batch unrelated
edits into one commit, and don't leave a working tree dirty at the end of
a task. After any content edit, code change, new blog publish, or asset
update:

```
git add <the specific files that changed>
git commit -m "<concise, why-focused message>"
```

Prefer staging specific paths over `git add -A`/`git add .` when the
change set is broad, so nothing unintended (stray local files, generated
junk) gets swept in — check `git status` before committing broad changes.
Never commit blog drafts (`blogs/*.md`, `blogs/images/`) — they're
gitignored on purpose (see "Blogs").

## Blogs — how content actually gets published

**A post is written in markdown locally and only its compiled HTML is
committed and pushed.** The draft (`blogs/<slug>.md`) and its source
images (`blogs/images/`) are gitignored: a build step (`publish_blog.py`)
converts the markdown into `blogs/<slug>.html`, and that page plus its
copied images and manifest entry are what ship (steering D-24). Keep your
own backup of drafts you care about — git won't have them.

Where post ideas come from is an open question in
`steering/direction.md` (the hub's Luma page is mentioned as a source).

### Why HTML output instead of client-side markdown rendering

Rendering markdown in the browser would mean post content is invisible to
crawlers until JS runs, and it's one more render-blocking fetch. A
pre-rendered static `.html` file per post is fast, fully indexable on its
own (own canonical URL, OG tags, JSON-LD `BlogPosting`), and needs nothing
from the reader but an HTTP GET.

### Authoring flow

1. Write the draft as `blogs/<slug>.md` with YAML frontmatter:

   ```markdown
   ---
   title: Teaching AI in our own languages
   date: 2026-04-12
   topics: [Education, AI Literacy]
   tags: [shona, ndebele, ai-literacy, education]
   image: images/hero.jpg   # path relative to the draft; becomes the post's hero + OG image
   authors: [Tariro M., Brandon T. Bande]   # 1 or 2 names; or `author: Name` for one
   featured: true   # optional — marks the post as a "Top story" on the blog listing
   excerpt: Why AI literacy lands differently in Shona and Ndebele.
   ---

   Body in markdown. Reference any inline images with normal markdown
   image syntax and a relative path — they get copied automatically.
   ```

   Required fields: `title`, `date` (YYYY-MM-DD), `topics`, `tags`,
   `image`, and an author line — **every post has 1 or 2 authors, never
   more**: `authors: [Name1, Name2]` (or `author: Name` for one). Two
   authors are joined as "A & B" for the byline/meta, and each gets their
   own `article:author` tag and JSON-LD author node (named people become
   `Person`; house bylines ending in "Team" stay `Organization`). A post
   is not considered complete without at least one image. The compiled
   page's share image (`og:image`/`twitter:image`/JSON-LD, with alt text)
   is **always the hub logo** for brand consistency — the frontmatter
   `image` is only the on-page hero and the listing-card thumbnail. Every
   compiled post ends with a standing disclaimer (baked into
   `scripts/_blog_template.html`, inside `.content` so the hologram
   reading panel shows it too): the views are the author(s)' own, not
   necessarily the Hub's; the Hub permits sharing of thoughts as long as
   they are not discriminatory.
   Put source images referenced by drafts in `blogs/images/` (distinct
   from `assets/blogs/<slug>/`, which holds the copies the compiled page
   actually serves).

2. Run the publish script (committed; install deps once with
   `pip install pyyaml markdown`), then refresh everything generated:

   ```
   python scripts/publish_blog.py blogs/<slug>.md
   python scripts/update_site.py
   ```

   The first renders `blogs/<slug>.html` from `scripts/_blog_template.html`,
   copies the hero + any inline images into `assets/blogs/<slug>/`, and
   updates `blogs/manifest.json`. The second renders the post into the
   home page's Blogs section and the blog cards, and refreshes `feed.xml`
   and `sitemap.xml`.

3. Review the generated `blogs/<slug>.html`, then commit the output only
   (never the `.md`):

   ```
   git add blogs/<slug>.html assets/blogs/<slug> blogs/manifest.json blogs/index.html index.html feed.xml sitemap.xml
   git commit -m "Add blog post: <title>"
   ```

   The script prints this exact command at the end of a successful run.

**Removing a post:** delete `blogs/<slug>.html` and `assets/blogs/<slug>/`,
remove its entry from `blogs/manifest.json`, run `update_site.py`, commit.

### Why drafts stay local

GitHub Pages runs Jekyll, which turns any pushed `.md` file into a public
page — a pushed draft became a duplicate, unlinked copy of its own post.
Keeping drafts out of git means only the compiled page is ever public.

## Read-more sidebar (data-driven)

Any item in a `data.json` section can carry a `more` object — clicking that
item in the 3D scene's holo panel opens the hologram side panel instead of
the inline expander. `prerender_seo.py` renders each `more` into a panel
inside `#hub-content` (`panel_html()`), and `openSide()` in `index.html`
clones that panel into the sidebar and wires it up (person cards, forms,
post fetches). Adding entries never requires HTML/CSS changes — but if you
change panel markup, change both sides (each carries a comment saying so).
Panel images are rendered as `data-src` and only load when a panel opens.
The `more` fields you can set in `data.json`:

- `more.body` — array of paragraphs.
- `more.title` / `more.kicker` / `more.meta` — header fields (kicker
  defaults to the section title, title to the item label).
- `more.image` — hero image path (site-root relative).
- `more.link` — `{ "href", "label" }`, rendered as a CTA button.
- `more.fetch` (set automatically for blog items) — the post page whose
  `.content` block is loaded into the panel when it opens; until then, and
  if loading fails, the panel shows `more.fallback` (the excerpt).
- `more.people: "leadership" | "members" | "all"` — renders the Team
  section's people (from `data/team/`, see "People and projects"):
  `leadership` as full-profile cards, `members` as a two-column grid,
  `all` as both. Every card opens that person's own panel
  (`#team/<slug>`, with a back button to the list). A blank photo falls
  back to an initials avatar;
  `itu` and `socials` render as an icon-link row. `more.empty` is shown when
  the requested group has nobody in it yet.
- `more.form` — renders a form that writes to Firebase (see "Forms").
- Section-level `empty` — text the holo panel shows when the section has
  no items (Blogs and Projects use it while they're empty).
- Item-level `group` — consecutive items with the same `group` get a small
  header in the holo panel (Projects uses "Community projects" /
  "Member projects").

Links are external-aware: `item.link` / `more.link.href` pointing off-site
open in a new tab (`target="_blank" rel="noopener"`). Use `item.link` with
no `more` for an item that simply points off the site (e.g. the Events
section's "All events on Luma" item).

**No links to standalone pages** (steering D-31): person, project and post
pages exist only as search-engine landing pages. Nothing on the site links
to them — every internal link is a `#<section>/<slug>` deep link that
opens the content in the sidebar (including the blog listing cards and the
links inside those standalone pages). Search engines find them through
`sitemap.xml` (and posts through `feed.xml`).

**Deep links**: every focused section and open panel is addressable —
`#<sectionId>` focuses that anchor (e.g. `#team`), and
`#<sectionId>/<item-slug>` also opens the item's panel (e.g.
`#team/hub-leadership`, `#blogs/<post-slug>`, `#team/<person-slug>`,
`#projects/<project-slug>`). Item slugs are derived from the label
(lowercased, hyphenated); blog, person and project items use their file
slug. A section-only hash closes any open panel. The URL hash updates as
panels open/close, so any view can be shared as a link.

**Events**: unlike blogs, event items are hand-maintained in `data.json`
(no live sync with Luma) — each carries `more.meta` (date · location),
`more.image` (hotlinked Luma cover image), `more.body`, and
`more.link` to the event's own `https://luma.com/<slug>` page. When
adding/updating events, pull details from
`https://luma.com/user/yailgweru`.

**Blogs in the sidebar**: blog items are rendered from
`blogs/manifest.json` at build time and the panel is the reading
experience — it loads the full article body from the post's own
`blogs/<slug>.html` when opened (the one copy of the text). The post pages
stay as the canonical, indexable copies.

## People and projects

Each person and project is **one JSON file; its filename is its slug**
(lowercase, hyphenated — `jane-doe.json`). These files are for updating
only; `python scripts/update_site.py` renders them into:

- their panels in the home page's hologram sidebar (`#team/<slug>`,
  `#projects/<slug>`), inside `index.html`'s `#hub-content` tree — this is
  where visitors see them, and
- a standalone SEO landing page — `team/<slug>.html` /
  `projects/<slug>.html` — with its own canonical URL, OG tags and JSON-LD
  (`ProfilePage` + `Person` for people, `CreativeWork` for projects),
  listed in `sitemap.xml` but not linked from anywhere on the site.

Never hand-edit the generated pages; `build_pages.py` deletes a generated
page when its JSON is deleted.

**Person** — `data/team/<slug>.json`:

```json
{
  "name": "Jane Doe",
  "group": "member",              // "leadership" or "member" (required)
  "order": 1,                     // sort order within the group (optional)
  "role": "Software Engineering",
  "image": "",                    // blank = auto-detect assets/team/<slug>.jpg|.jpeg|.png|.webp
  "brief": "One line for cards and the page description (optional; defaults to the first bio paragraph).",
  "bio": ["Paragraph one.", "Paragraph two."],
  "projects": [],                 // optional: project slugs this person works on (adds them as a team member)
  "itu": "",                      // their ITU / AI for Good profile — must be an *.itu.int URL
  "socials": {                    // full https:// URLs; leave unused ones blank
    "linkedin": "", "x": "", "github": "", "instagram": "",
    "facebook": "", "youtube": "", "website": ""
  }
}
```

**Every person needs an `itu` profile and at least 2 socials** (steering
D-33). The build still runs without them, but `update_site.py` lists each
incomplete profile until they're filled. The ITU profile is shown first in
the icon row and every link goes into the person's JSON-LD `sameAs`. To add
a new platform, add it to `SOCIALS` in `scripts/site_content.py` and drop a
matching icon in `assets/icons/`.

Photos for leadership and members alike go in `assets/team/`, named by
slug (`assets/team/jane-doe.jpg`); square crops around 400×400 look best.

**Project** — `data/projects/<slug>.json`:

```json
{
  "title": "AI Literacy for All",
  "ownership": "community",       // "community" (hub-run) or "member" (owned by members) — required
  "owners": ["jane-doe", "john-roe"], // team slugs; any number (co-ownership). Required for member projects, optional "leads" for community ones
  "members": ["sam-moyo"],        // team slugs of people working on it who aren't owners (optional)
  "sdgs": [4, 9],                 // UN Sustainable Development Goal numbers 1–17 (at least one, required)
  "status": "active",             // "planned" | "active" | "completed" | "" (optional)
  "order": 1,
  "summary": "One line — shown in lists, bold on the page (required).",
  "body": ["Paragraph one.", "Paragraph two."],
  "image": "",                    // blank = auto-detect assets/projects/<slug>.*; images are optional
  "links": [{ "href": "https://…", "label": "Repo →" }]
}
```

Community projects list first, then member projects.

**Tagging people and projects** works from either side. A project's
`owners` and `members`, plus any person who lists the project in their own
`projects`, are all linked both ways. The project panel shows "Owned by" /
"Co-owned by" / "Led by" and "Team". Each person's panel lists their
projects with their role (Owner, Co-owner, Lead, Team member) and the SDGs
those projects work towards. SDG tags link to the goal on `sdgs.un.org` and
go into the project's JSON-LD (`about`, `keywords`).

**Filters:** the Projects holo panel has "SDG" and "Person" dropdowns
(`filter_template()` in `prerender_seo.py`, wired in `openHolo()` in
`index.html`). They list only the SDGs and people actually tagged on
projects, and match against each project's `data-sdgs` / `data-people`.

`build_pages.py` refuses to write anything if a file is invalid (unknown
owner/member/project slug, SDG outside 1–17, unknown social key, non-ITU
`itu` URL, bad URL, missing image, slug clashing with a Team item like
`join-the-hub`) and prints every problem.

## Forms (Firebase)

"Join the hub" (Team) and "Become a partner" (Partners) are forms defined
in `data.json` as `more.form`:

```json
"form": {
  "collection": "joinRequests",   // Firestore collection the submission is written to
  "submitLabel": "Send application",
  "success": "Shown after a successful submit.",
  "offline": "Shown (and submit disabled) until Firebase is configured.",
  "fields": [
    { "name": "email", "label": "Email", "type": "email", "required": true, "max": 200 }
  ]
}
```

Field types: `text`, `email`, `tel`, `url`, `textarea` (all need `max`),
`select` (needs `options`), `checkbox` (a required checkbox must be
ticked). Each submission also gets a server `createdAt`, and a hidden
honeypot field silently drops bot submissions.

`build_form_rules.py` generates `firebase/firestore.rules` from these same
definitions: form collections are **create-only** (the public site can't
read, edit or delete submissions), and every field is checked for type,
length, allowed options and required-ness. Change a form only in
`data.json`, then run `update_site.py` and redeploy the rules.

The Firebase SDK (`firebase-firestore-lite`, from `gstatic.com`) is only
downloaded when someone submits, so it costs nothing on page load.

**Setup / changes** (one-time setup is done in the Firebase console):

1. Create a Firebase project, add a **Web app**, and enable **Cloud
   Firestore** (production mode).
2. Paste the web app's config into `data.json` → `firebase` (`apiKey`,
   `authDomain`, `projectId`, `appId`). These values are public by
   design; the rules are what protect the data.
3. Deploy the rules: `cd firebase && firebase use --add` (once), then
   `firebase deploy --only firestore:rules` — Firebase compiles and checks
   the rules on deploy. Redeploy whenever a form changes.
4. Run `python scripts/update_site.py`, commit, push. Submissions appear in
   the Firebase console under Firestore → Data.

## Assets

- **Favicon** (`assets/favicon/`): a full set generated from
  `assets/logo.png` — `favicon.ico` (16/32/48 multi-res), standalone
  16/32/48/96px PNGs, `apple-touch-icon.png` (180px), Android Chrome icons
  (192/512px), and `site.webmanifest`. All referenced from `<head>` in
  both `index.html` and the blog template. If `logo.png` changes, rerun
  `python scripts/make_favicons.py` to regenerate the whole set — don't
  hand-edit the generated files.
- **Fonts** (`assets/fonts/`): empty today by design — the site uses the
  system font stack (`Segoe UI`/`system-ui`), so there are zero external
  font requests and no font-swap flash. If a custom font is ever added,
  self-host the `.woff2` files here rather than pulling from a Google
  Fonts/Adobe Fonts CDN — see `assets/fonts/README.md` for the exact
  `@font-face` pattern (with `font-display: swap` and a system-font
  fallback). Third-party font CDNs add a render-blocking round trip and a
  visible layout shift once the font arrives; self-hosting avoids both.
- **Blog images** (`assets/blogs/<slug>/`): populated automatically by
  `publish_blog.py` — don't add images here by hand, add them to the
  markdown draft instead so the manifest/OG tags stay correct.
- **Team photos** (`assets/team/`) and **project images**
  (`assets/projects/`, optional): named `<slug>.jpg|.jpeg|.png|.webp` and
  picked up automatically by `build_pages.py` — see "People and projects".
- **Icons** (`assets/icons/`): small inline-style SVGs used by the
  hologram sidebar (one per `SOCIALS` key in `site_content.py`, plus
  `itu.svg` for the ITU profile, for the social
  row on team profile/member cards). Hand-authored, not generated — keep
  new ones in the same minimal single-color style (`#6be8ff` stroke/fill,
  24×24 viewBox).

## SEO

- **All content is rendered into the static HTML** by
  `python scripts/prerender_seo.py` (via `update_site.py`), which rewrites
  generated marker blocks: `INLINE-SEO-HEAD` (title/meta/OG/Twitter/
  canonical/RSS link) and `INLINE-LD-JSON` (Organization + WebSite
  `@graph`) in `index.html`'s head; `INLINE-BRAND` (brand bar + hint) and
  `INLINE-CONTENT` (the `#hub-content` tree: every section, item and
  sidebar panel as semantic HTML) in its body; and `INLINE-BLOG-LIST`
  (post cards) in `blogs/index.html`. Crawlers read exactly what the
  sidebar shows. Edit copy in `data.json` / `data/`, never in the
  generated blocks.
- The panel markup in `prerender_seo.py` and the card markup in
  `blogs/index.html`'s filter script are read by the page JS — if you
  change markup on one side, change the other (both carry comments).
- Every blog post, person and project gets its own canonical URL,
  OG/Twitter tags and JSON-LD — generated by `publish_blog.py` /
  `build_pages.py`, don't hand-write these. Share images are always the
  hub logo (steering D-16).
- `sitemap.xml` is **generated** by `build_sitemap.py` (last step of
  `update_site.py`): `/`, `/blogs/`, every post, every project and every
  person page, with `lastmod` taken from git. Don't hand-edit it; if you
  ever add a new kind of page, add it to that script.
- SEO targets Zimbabwe, Gweru and Southern Africa first (steering D-23) —
  keep new copy and keywords in that frame.
- **RSS**: `feed.xml` (generated by `build_feed.py`) lists every post with
  its full text; items link to `#blogs/<slug>`. Pages advertise it with
  `<link rel="alternate" type="application/rss+xml">` in their heads.
- `robots.txt` points at the sitemap — keep it that way.

## Mobile-friendliness

- Viewport meta is `width=device-width, initial-scale=1.0,
  viewport-fit=cover` — **do not** add `user-scalable=no` or
  `maximum-scale=1.0` back; disabling pinch-zoom fails accessibility and
  mobile-friendliness checks.
- The 3D scene's mobile breakpoint is `max-width: 640px` in
  `index.html`'s `<style>` — mobile gets a smaller holo-panel positioned
  bottom-center, larger tap targets (buttons ≥ 40px), and
  `env(safe-area-inset-*)` padding so UI doesn't sit under notches/home
  indicators on iOS.
- Blog pages (`scripts/_blog_template.html`, `blogs/index.html`) are plain
  responsive HTML/CSS with a single `max-width` wrapper and a 640px
  breakpoint — no JS layout logic, so they can't break on odd viewports.
- When changing any layout CSS, check both the home page (3D scene) and a
  blog post at a narrow width (≈375px) and a short one (≈650px tall) —
  the home page in particular is easy to break on short viewports since
  the canvas is `position: fixed; inset: 0`.

## Conventions to keep in mind

- Don't hardcode copy into `index.html` — it belongs in `data.json`.
- Don't hand-write a `blogs/<slug>.html` file — always go through
  `blogs/<slug>.md` + `publish_blog.py` so metadata, images, the
  manifest, and the sitemap stay consistent. Never commit the `.md`.
- Don't hand-edit anything in `team/`, `projects/`, `sitemap.xml`,
  `feed.xml` or `firebase/firestore.rules` — they're generated from
  `data/`, `data.json` and the blog list by `update_site.py`.
- Don't make the page read JSON at runtime, and don't link to the
  standalone person/project/post pages — render content into
  `#hub-content` and link with `#<section>/<slug>` deep links.
- Don't add a build step, framework, or package.json unless there's a
  concrete reason — the zero-build-step property is intentional.
- Don't hand-edit the generated blocks — `INLINE-SEO-HEAD`,
  `INLINE-LD-JSON`, `INLINE-BRAND`, `INLINE-CONTENT`, `INLINE-LOGO` (in
  `index.html`) or `INLINE-BLOG-LIST` (in `blogs/index.html`). Rerun
  `python scripts/update_site.py` and commit the result.
